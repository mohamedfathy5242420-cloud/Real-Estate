# Decisions

## مؤكد
D001: بروكر واحد، عدة مطورين.
D002: Clean Architecture حسب الطبقة والنوع؛ بدون Vertical Slice.
D003: المطور بلا حساب، والتواصل خارجي وموظف البروكر يسجل النتيجة.
D004: حساب للعميل؛ التصفح عام وطلبات المعاينة والحجز تحتاج تسجيل الدخول.
D005: إسناد يدوي من المدير؛ الطلبات التالية لنفس الموظف، مع تاريخ النقل.
D006: اقتراح العميل للموعد يحتاج تأكيدًا؛ البديل المنسق يحتاج قبول العميل.
D007: الإلغاء وإعادة الجدولة قبل الموعد؛ إعادة الجدولة تلغي القديم فورًا.
D008: الحالة ظاهرة للعميل، والملاحظات داخلية للموظف المسؤول والمدير.
D009: طلب الحجز لا يشترط معاينة ولا يثبت الحجز.
D010: نظام مراحل وخطوات وتحقق وتسليم ومراجعات داخل Repo.
D011: تصحيح المستخدم 2026-09-21: تجهيز Workflow فقط، وليس كتابة التطبيق.
تم سحب الهيكل البرمجي الذي أنشأه المساعد بالخطأ.

## قرارات الاستمرار
D012 (Accepted): المستخدم اختار Angular وطلب Workflow مستقلًا داخل front end.
D013 (Accepted): المستخدم طلب بدء Backend من الملفات؛ انتقل العمل من إعداد Workflow إلى P01 حسب الخطة.
D011 يظل سجلًا لتصحيح سابق، وقيد Workflow-only الحالي استبدل بطلب D013.

## قرار ربط Business
D014 (Accepted): طلب المستخدم دمج Business وWorkflow في ملفات يقرأها أي Agent لاحقًا؛ docs/business مرجع تفصيلي مرتبط بالخطوات والقبول.

## قرارات اتفاق التسويق والعمولة والـLeads (2026-09-23)
D015 (Accepted): الاتفاق يتبع مطورًا واحدًا، ونطاقه صريح: كل مشاريع المطور الحالية والجديدة أو مشاريع محددة.
D016 (Accepted): العمولة نسبة من سعر البيع النهائي دون الرسوم والإضافات، أو مبلغ ثابت.
D017 (Accepted): قاعدة افتراضية للاتفاق مع Override للمشروع فقط.
D018 (Accepted): الصفقة تحفظ Snapshot لقاعدة العمولة والسعر والقيمة.
D019 (Accepted): منع تداخل اتفاقين فعالين يغطيان المشروع نفسه في الفترة نفسها.
D020 (Accepted): Lead فرصة بيع مرتبطة بعميل ومشروع.
D021 (Accepted): مدة حماية افتراضية 90 يومًا قابلة للتعديل أو الصفر، للـLeads المسجلة أثناء سريان الاتفاق، بشرط اكتمال البيع خلال الحماية.
D022 (Accepted): الإسناد الأساسي للعميل (Customer Assignment)، وليس توزيع كل Lead تلقائيًا على موظف مختلف.
هذه التفاصيل تغلق Q02 لنطاق S04. التحويل بين العملات، الشرائح، عمولة مستوى الوحدة،
تقويم العمل وآلية التجديد خارج القرار الحالي ولا تُخترع ضمن التنفيذ.

## قرارات المعاينات Q03 (2026-09-23)
D023 (Accepted): العميل يقترح وقت البداية؛ المدة الافتراضية 60 دقيقة، والموظف يثبت البداية والنهاية عند التأكيد.
D024 (Accepted): أقصى موعد يقترحه العميل 30 يومًا مقدمًا.
D025 (Accepted): PendingConfirmation تنتهي بعد سبعة أيام أو عند الوقت المقترح أيهما أقرب؛ AwaitingCustomerAcceptance تنتهي عند وقت البديل.
D026 (Accepted): الفترة تُحجز عند Confirmed فقط؛ أول تأكيد صحيح يفوز، ويمنع تداخل نفس الوحدة أو الموظف؛ الطلب المتعارض يبقى Pending لبديل.
D027 (Accepted): إعادة الجدولة تلغي الموعد المؤكد القديم فورًا، والجديد يحتاج دورة تأكيد.
D028 (Accepted): المعاينة المؤكدة لا تنتهي تلقائيًا بمرور الوقت؛ تنتظر Completed أو CustomerNoShow أو إلغاءً صحيحًا.
D029 (Accepted): CustomerNoShow لغياب العميل فقط؛ إلغاء الموظف أو عدم توفر المطور يسجل Cancelled مع الفاعل والسبب والإخطار.
D030 (Accepted): أوقات المعاينات تحفظ UTC وتعرض بالتوقيت المناسب للمشروع/المستخدم.

## قرار تأجيل الاختبارات الآلية في البداية (2026-09-23)
D031 (Accepted): بناءً على طلب المستخدم، لا تكون كتابة أو تشغيل Unit/Architecture/
Integration tests شرطًا لإغلاق P02-S01 أو بدء أول Business feature. تظل مشاريع الاختبار
الفارغة داخل الـSolution لتعلّم الاختبارات وإضافتها تدريجيًا في خطوة مستقلة لاحقًا، ولا نضع
اختبارات وهمية لمجرد الحصول على نتيجة خضراء. يظل `restore` و`build` وفحص `/healthz`
والتحقق اليدوي من Project References إلزاميًا لخطوة التأسيس.
D032 (Accepted): P02-S01 يثبت .NET 10 LTS SDK 10.0.401 وTargetFramework `net10.0`،
مع `global.json` وإدارة إصدارات NuGet مركزيًا.

## قرارات الهوية وقاعدة البيانات (2026-09-26)
D033 (Accepted): ASP.NET Core Identity هو مخزن الحسابات؛ تسجيل الدخول بالبريد وكلمة المرور،
وجلسة Angular تستخدم Cookie آمنة `HttpOnly` و`Secure` بدل حفظ token في JavaScript.
D034 (Accepted): العميل يستطيع إنشاء حسابه بنفسه، أما حسابات الموظفين والمدير والإدارة
فينشئها System Administrator. تأكيد البريد مطلوب قبل طلب معاينة أو حجز، واسترجاع كلمة
المرور يتم برابط بريد. الهاتف مطلوب للتواصل وليس اسم دخول.
D035 (Accepted): `Customer` سجل CRM مستقل عن حساب Identity. لا يتم الربط التلقائي بسبب
تشابه الهاتف أو البريد؛ الربط يحتاج ملكية حساب مؤكدة وطلب ربط يراجعه المدير، مع حفظ الأثر.
D036 (Accepted): قاعدة البيانات Microsoft SQL Server مع EF Core SQL Server provider.
التطوير المحلي يستخدم SQL Server Express وWindows authentication دون حفظ كلمة مرور في Repo.
إصدارات Identity وEF Core المثبتة في P02-S03 هي 10.0.12 ومتوافقة مع `net10.0`.
