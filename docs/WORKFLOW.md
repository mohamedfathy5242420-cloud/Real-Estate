# طريقة العمل

## المصدر
مبني على ترتيب الشات المرجعي:
Phases → Steps → 4 Validation Layers → Scripts → Definition of Done → Handoffs → Phase Reviews.
تعريف الطبقات الأربع هنا تكييف مقترح؛ تفاصيلها الأصلية لم تظهر في الجزء المقروء.

## المرجع
ملفات المشروع هي الذاكرة المشتركة. قرار المستخدم الأحدث يعلو على المسودة السابقة.
CURRENT_STATE هو مصدر الحالة؛ CURRENT_HANDOFF يطابقه.
نسجل القرارات وأسبابها وأثرها بدل الاعتماد على ذاكرة المحادثة.

## دورة العمل
قبل أي خطوة: اقرأ docs/business/README.md ثم مراجع BR/UC/AC الخاصة بها.
TRACEABILITY.json يربط الرحلات بمراحل التنفيذ والأسئلة المفتوحة؛ وجود الرابط لا يعني تنفيذها.
مطلوب في كل خطوة BusinessRefs وUseCaseRefs وAcceptanceRefs، أو N/A مع سبب للخطوة التقنية البحتة.
1. قراءة السياق والقرارات والحالة والتسليم.
2. تجهيز المرحلة: الهدف والنطاق والاعتماديات والخطوات ومعايير الإكمال.
3. تجهيز الخطوة: نتيجة واحدة، ملفات مسموحة، معايير قبول وحالات فشل.
4. التنفيذ داخل النطاق المصرح به وتوثيق الافتراضات.
5. التحقق بالأربع طبقات المناسبة وتسجيل الأدلة الفعلية.
6. مراجعة النتيجة مقابل معايير القبول وإصلاح الملاحظات.
7. تحديث الحالة والقرارات والمخاطر والتسليم وتقديم شرح للمستخدم.
8. مراجعة نهاية المرحلة: جمع أدلة الخطوات وقبول النتيجة كاملة.

## حالات الخطوة
Draft → Ready → InProgress → InReview → Done.
Blocked له سبب محدد وطريقة استئناف. تصحيح ملاحظة يعيد الخطوة إلى InProgress.
لا يوجد أكثر من خطوة InProgress. لا Done دون أدلة ومراجعة.

## الأدوار
المخطط يحدد النطاق والقبول، والمنفذ يقدم النتيجة والأدلة، والمراجع يفحصهما.
يجوز أن يقوم نفس المساعد بالأدوار بالتتابع؛ نسمي ذلك مراجعة ذاتية.
تغيير الموديل يدوي حسب اختيار المستخدم، ولا يعني تشغيل وكلاء تلقائيًا.

## Definition of Done للخطوة
كل معيار قبول له دليل، والفحوص المناسبة نجحت، وغير المناسب له سبب N/A.
لا عيب يمنع القبول؛ المؤجل موثق. الحالة والتسليم والقرارات محدثة.
المراجع ونوع المراجعة والنتيجة واضحون.
اختبارات التنفيذ تحمل مراجع AC/BR المناسبة، ويحدث testEvidence بالخريطة بعد تشغيلها فعلًا.
تغيير Business يحدث القاعدة والرحلة والسيناريو والخريطة والقرارات وعقد Frontend المتأثر.

## Definition of Done للمرحلة
كل الخطوات المطلوبة مكتملة، وسيناريو المرحلة متحقق، وPHASE_REVIEW يسجل النتيجة والفجوات.
نجاح build وحده لا يكفي.

## حدود الاستقلالية
لا نكرر طلب الموافقة على العمل الروتيني المصرح به.
وجود خطة ليس تصريحًا بتنفيذها. طلب المستخدم الأخير بدأ Backend؛ المرجع للنطاق النشط هو CURRENT_STATE.

## Phase branches
Follow docs/GIT_WORKFLOW.md: each phase has a descriptive backend/pNN-* or frontend/fNN-* branch. Record branch and commit in evidence and handoff.
